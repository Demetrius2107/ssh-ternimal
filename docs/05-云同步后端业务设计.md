# 云同步后端业务设计（server 模块，M7）

> 更新：2026-08-16
> 级别：核心业务设计（L1，完整 5 阶段分析）
> 架构：同仓库 `server/` 子目录（独立 Go module），客户端 `ssh-terminal` 仅做本地加密与推送/拉取
> 零知识原则：**服务端只存储密文，永不解密**（密钥仅存在于用户口令派生，服务端不可见）

---

## 1. 场景建模

### 1.1 角色
| 角色 | 说明 |
|---|---|
| 用户 | 注册/登录，管理自己的 Vault 数据与设备 |
| 设备 | 用户的一台客户端（桌面）；每设备一个凭据，可单独撤销 |
| 服务端 | 存储密文、校验令牌、维护版本号（不可解密） |

### 1.2 核心用例
1. 注册账户 → 创建用户 + 主设备
2. 登录 → 换取访问令牌
3. 上传 Vault（加密串 + 版本）→ 服务端保存为新版本
4. 拉取 Vault → 返回最新版本密文与版本号
5. 多设备同步：B 设备拉取 → 本地合并 → 推送新版本
6. 设备管理：列出/撤销设备（如换机/丢失）
7. 删除账户（可选）

### 1.3 边界用例
- 同一账户在 2+ 台设备上修改 Vault → 版本冲突
- 断网重传（上传成功但客户端未收到确认）→ 幂等
- 用户忘记备份口令 → 数据不可恢复（必须明示，无找回通道）

## 2. 业务规则提炼

### 2.1 显性规则
- R1：Vault 数据以"版本号 + 密文 + 更新时间"三元组存储，每次上传版本号 +1。
- R2：上传仅接受 `版本号 == 服务端当前版本 + 1`（顺序提交）；否则视为冲突返回 409。
- R3：拉取返回当前最新版本与密文，不要求前置条件。
- R4：设备凭据（令牌）独立于账户密码；撤销设备使其令牌立即失效。
- R5：注册时创建主设备，主设备不因登录过期而丢失。

### 2.2 隐性规则
- R6：密文不可分块——整体替换（不增量 diff），避免服务端了解内容结构。
- R7：冲突由客户端解决（last-write-wins 默认 + 提示用户），服务端不做内容合并。
- R8：同一设备重复上传同一版本视为幂等重试，直接返回成功（见一致性）。

### 2.3 边界规则
- R9：上传密文大小上限（如 4MB），超限拒绝。
- R10：版本号不回退；若客户端本地版本高于服务端（服务端数据被删/回滚），以客户端为准重新播种。
- R11：30 天未活跃的设备标记为"可能失效"，由用户确认后撤销。

### 2.4 并发规则
- R12：版本号 +1 的检查必须在数据库**单事务内**完成（`UPDATE ... WHERE version = ?` 原子性），防止并发上传竞态。
- R13：同账户多设备同时拉取/推送，以事务隔离保证版本单调递增。

## 3. 状态机与事件

### 3.1 账户状态
```
pending(注册中) → active(正常) → locked(连续登录失败/安全事件) → deleted
```
- pending→active：完成注册（含主设备创建）
- active→locked：5 次连续登录失败（锁定 15 分钟）
- active→deleted：用户确认删除（级联删数据与设备令牌）

### 3.2 设备状态
```
active → revoked
```
- active→revoked：用户手动撤销 / 30 天不活跃确认 / 账户锁定
- revoked 后其令牌立即 401

### 3.3 Vault 版本事件流
```
初始:  version=0, 无数据
上传:  version=0 → 1（首次）→ 2 → ...（每次 +1）
冲突:  客户端提交 version=1 但服务端已是 2 → 409 + 返回服务端最新版本
重试:  客户端基于最新版重新合并后再次提交
```

## 4. 异常与一致性

| 场景 | 处理 | 一致性策略 |
|---|---|---|
| 上传后客户端断网未收到确认 | 客户端重试同版本上传 → 服务端幂等返回成功 | 幂等（版本相同即成功） |
| 多设备同时修改 | 后提交方收到 409，提示冲突，客户端选择"用我的/用它的/手动" | last-write-wins 默认 + 用户干预 |
| 服务端数据被删/回滚 | 客户端版本 > 服务端版本 → 以客户端为准重新播种 | 单调版本 + 客户端权威 |
| 网络超时/5xx | 客户端指数退避重试（2s/4s/8s，最多 3 次） | 重试幂等 |
| 密码丢失 | 密文不可解密（零知识）→ 明示"备份口令即备份数据" | 不可恢复是设计特性 |
| 数据库写失败 | 返回 500，版本号不变，客户端可安全重试 | 事务原子性 |

## 5. 安全与合规

### 5.1 认证与会话
- 口令：**PBKDF2-HMAC-SHA256（迭代 60 万，随机盐）** 存储口令哈希（复用 `internal/vault` 的派生参数）。
- 令牌：JWT（HS256，服务端密钥），有效期 24h；登录返回 `access_token + refresh_token`（refresh 7 天）。
- 设备令牌：独立于 JWT 的设备 ID + 随机密钥，撤销设备即删除其密钥。

### 5.2 传输与存储
- 全链路 HTTPS（生产）；本地开发 HTTP 仅限 localhost。
- 存储：仅存密文 + 元数据（版本/时间/设备）；**不存口令、不存明文、无解密路径**。
- 数据库字段最小化：user(id, email, pwd_hash, salt, status)、device(id, user_id, name, secret_hash, status)、vault(user_id, version, ciphertext, updated_at)。

### 5.3 合规与审计
- 登录/注册/上传/拉取/撤销全部记录审计日志（谁、何时、哪台设备、动作）。
- 数据主体权利预留：导出本人全部数据、删除账户级联清除。
- 最小权限：服务端无任何"重置密码后恢复数据"功能（零知识承诺）。

## 6. 接口契约（草案）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | /api/register | {email, password} | {token, refresh, deviceId} |
| POST | /api/login | {email, password} | {token, refresh} |
| GET | /api/vault | - | {version, ciphertext, updatedAt} |
| PUT | /api/vault | {version, ciphertext} | 200 {version+1} / 409 {latestVersion} |
| GET | /api/devices | - | [{id, name, status, lastActive}] |
| DELETE | /api/devices/{id} | - | 204 |
| POST | /api/refresh | {refresh} | {token, refresh} |

> 冲突交互：客户端收到 409 后，用响应中的 `latestVersion` 重新拉取 → 本地合并（默认 last-write-wins，可提示用户）→ 以最新版本重试提交。

## 7. 技术选型建议

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/框架 | Go + net/http（标准库路由，轻量） | 与客户端同栈；零额外依赖 |
| 数据库 | SQLite（单文件，个人/小团队够用）→ 可迁 Postgres | 部署简单；版本更新原子性靠事务 |
| 令牌 | JWT 手写签发（标准库 + crypto） | 避免引入大依赖 |
| 部署 | 单二进制 + SQLite 文件；可选 Docker | 个人 VPS 直接跑 |
| 密码哈希 | PBKDF2（复用 vault 包参数） | 与客户端加密派生一致 |
